== Purpose of this roadmap

This roadmap defines a realistic path for Nickel Augmentation as a practical toolkit built on Nickel.

It intentionally narrows scope.

The project may contain ambitious ideas, but the roadmap prioritises work that produces a coherent repository, demonstrable value, and clear adoption paths. The aim is not to promise a new universe of language features all at once. The aim is to ship useful augmentation around Nickel in an honest sequence.

== Strategic direction

Nickel Augmentation should be understood as:

* a practical layer built on Nickel
* a home for reusable configuration patterns and contracts
* a place for artifact generation and configuration reporting
* a repository for operationally useful examples and templates

It should not treat every speculative possibility as a near-term deliverable.

That means:

* practical tooling comes before grand theory
* examples come before platform sprawl
* coherent documentation comes before ecosystem expansion
* experimental ideas are preserved, but clearly marked as experimental

== Success criteria

A successful near-to-medium-term version of this repository will provide:

* a clear repository identity
* practical, reusable Nickel patterns
* at least one end-to-end configuration generation flow
* reporting or inspection tooling that makes Nickel output easier to trust
* documentation that accurately distinguishes implemented, partial, and experimental work

== Phase 0 — Identity and documentation cleanup

=== Goal

Make the repository legible and internally consistent.

=== Why this phase matters

At present, the main obstacle is not lack of ideas. It is identity drift. Different files describe different repository purposes, structures, completion levels, and even licensing assumptions. That makes the project harder to evaluate, contribute to, and extend.

=== Deliverables

* Rewrite `README.adoc` so the top-level identity is consistent and practical.
* Rewrite `ROADMAP.adoc` to reflect phased delivery rather than a flat pile of ambitions.
* Update `CONTRIBUTING.md` to match the actual repository layout.
* Update `TOPOLOGY.md` so the structure description matches reality.
* Make machine-readable state files consistent with public documentation.
* Remove or rewrite stale text that describes missing directories, wrong project structure, or contradictory completion claims.
* Ensure subproject READMEs reinforce the top-level story instead of competing with it.

=== Exit criteria

Phase 0 is complete when a new visitor can understand:

* what the repo is for
* what the main subprojects are
* what is already real
* what is exploratory
* where to start

== Phase 1 — Core practical deliverables

=== Goal

Establish a compact, useful core that demonstrates why Nickel Augmentation exists.

=== Primary focus areas

==== 1. Reusable contract and module patterns

Build and document a small set of reusable patterns for configuration composition.

Examples might include:

* environment overlays
* contract-checked service definitions
* reusable metadata records
* default-and-override patterns
* policy-shaped configuration structures

The emphasis should be on examples people can understand and adapt.

==== 2. Artifact generation

Demonstrate clean flows from Nickel source definitions to generated artifacts such as:

* JSON
* YAML
* TOML
* text-based configuration fragments

The important thing is not the number of output formats but the clarity of the source-to-artifact path.

==== 3. Reporting and inspection

Strengthen `config-reporter/` or equivalent tooling so that users can inspect what a configuration resolves to.

Possible outputs include:

* summaries
* audits
* warnings
* field inventories
* contract coverage views
* provenance or explanation notes

==== 4. End-to-end examples

Provide at least one complete example showing:

* source Nickel definitions
* contract enforcement
* generation of downstream artifacts
* reporting or inspection output
* documentation for how to run the flow

=== Deliverables

* a documented core example set
* a small reusable pattern library
* one or more generation pipelines
* one or more readable reporting flows
* tests or validation examples for failure modes

=== Exit criteria

Phase 1 is complete when the repository can convincingly answer:

“Why should someone use this instead of plain YAML or JSON?”

== Phase 2 — Ecosystem integrations and applied patterns

=== Goal

Show how Nickel Augmentation fits into broader real-world workflows.

=== Focus areas

==== 1. CI/CD and repository workflows

Develop examples and patterns for generating or validating configuration used in:

* CI pipelines
* repository metadata
* automation definitions
* project templates

==== 2. Infrastructure-oriented examples

Add examples where Nickel serves as a disciplined source language for infrastructure-adjacent configuration without claiming to replace all existing infra tooling.

Possible examples:

* service manifests
* deployment descriptors
* environment matrices
* generated policy fragments
* structured operational metadata

==== 3. RSR-oriented patterns

Where relevant, formalise patterns useful to Rhodium Standard Repository style ecosystems:

* repository metadata shaping
* policy-aware defaults
* contract-oriented repository descriptors
* generated documentation fragments
* consistency checks

==== 4. Documentation on tradeoffs

Document when Nickel Augmentation is appropriate and when it is not.

This should include practical guidance such as:

* when plain TOML is enough
* when JSON/YAML become too brittle
* when Nickel adds value
* when a problem is really a language research problem rather than a configuration problem

=== Deliverables

* integration examples
* repository/workflow templates
* RSR-adjacent patterns where useful
* tradeoff documentation
* stronger examples of generation plus inspection

=== Exit criteria

Phase 2 is complete when the repo has multiple believable usage stories rather than a single abstract promise.

== Phase 3 — Experimental extensions

=== Goal

Preserve advanced ideas without letting them distort the main project identity.

=== Positioning

This phase is explicitly experimental.

Material in this phase should be labelled clearly as one or more of:

* design notes
* prototypes
* RFCs
* research directions
* upstream proposal candidates

=== Candidate experimental topics

These may be worth exploring, but should not be described as core implemented features unless they actually become so.

* richer refinement-like validation patterns
* dependent-style configuration helpers
* secret reference conventions
* temporal or lifecycle-oriented config modelling
* external verifier hooks
* richer interop/export pipelines
* editor or language tooling helpers specific to this repository

=== Rules for this phase

* Experimental work must not overwrite the practical identity of the repo.
* Speculative work should live in clearly marked locations.
* Documentation must distinguish “prototype” from “supported”.
* If an idea requires changes to Nickel itself, that should be said plainly.

=== Exit criteria

There is no requirement that Phase 3 be “completed” in the ordinary sense.

Its purpose is to create a safe place for ambitious work without confusing visitors about what the repository already delivers.

== Ongoing maintenance themes

These themes apply across all phases.

=== Coherence over expansion

The repository should become easier to understand over time, not merely larger.

=== Honest status reporting

Public documentation, topology, and machine-readable state should agree about maturity.

=== Demonstration over assertion

A small working example is more valuable than a large paragraph of future intent.

=== Local clarity first

Each subproject should have a clear local purpose and relationship to the repository as a whole.

== What is intentionally de-emphasised

The following ideas may still appear as experiments, but they are intentionally de-emphasised as top-level promises:

* full new type-theoretic ambitions
* language-fork framing
* all-encompassing secrets platform claims
* broad verification claims without working integrations
* editor ecosystem expansion as a first-class goal
* trying to become a universal infrastructure platform

These are not forbidden. They are simply not the primary near-term story.

== Risks

=== Identity drift

Different files may start telling different stories again.

Mitigation:
keep top-level docs, subproject docs, and state files aligned.

=== Overpromising

It is easy to describe a far larger platform than the repository currently implements.

Mitigation:
describe prototypes as prototypes and roadmap items as roadmap items.

=== Subproject fragmentation

Individual directories may evolve compelling local identities that no longer fit together.

Mitigation:
maintain a clear top-level narrative and revisit boundaries periodically.

=== Confusing research with product

Some ideas are language research, not near-term tooling.

Mitigation:
create a clear experimental track and keep the practical track separate.

== Next concrete actions

The recommended immediate sequence is:

. finalise the top-level README
. finalise this roadmap
. repair `CONTRIBUTING.md`
. repair `TOPOLOGY.md`
. align machine-readable state files
. choose one end-to-end example to make excellent
. expand only after that example is solid

== Maintainer note

When making roadmap decisions, prefer this question:

“Does this make Nickel Augmentation more useful, more coherent, or more demonstrable in practice?”

If the answer is no, the work may still be interesting, but it likely belongs in an experimental track rather than in the core project path.
